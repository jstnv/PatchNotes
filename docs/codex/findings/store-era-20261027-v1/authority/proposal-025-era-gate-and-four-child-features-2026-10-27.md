## Intent and scope

Grow the Store as a readable tree of useful child capabilities, with the first later-era cards gated by actual Studio progress as well as time. Introduce the era foundation before the four cards so 1986–88 children cannot be acquired by waiting through the calendar. Keep the current 42 Features, specialty grants, accepted Research, committed releases, and project supply intact. No Innovation victory, Genre/Theme entitlement, Pass upgrade, platform registry, Contract card, or final balance decision is part of this package.

This is **one coordinated implementation package with two ordered stages**: (A) versioned era receipt/quote/UI foundation, then (B) four authored Feature definitions and their map placement. Stage A must pass its own migration and locked-condition checks before Stage B can expose cards. PN Implementation owns authoritative `patch-notes/` adoption under `AGENTS.md`; this design thread owns this proposal and a subsequent source-pinned handoff. ## Stage A — proposed receipt and access contract

1. **Qualification:** one successfully committed, Studio-owned player release qualifies when its frozen played Scope is at least its **positive frozen required Scope**. Equality qualifies. A publisher-owned commission, failed/cancelled release, duplicate registration, raw release count, owned-pool Scope or later recomputation does not. This follows the prior [era review](../../../docs/codex/findings/queue-20261018-v1/ERA-PLATFORM-REVIEW.md); no Review threshold is added.
2. **One distinct release per successive era:** assign eligible release IDs in deterministic `(release_cycle, release_id)` order to the 1984, 1990, 2000, 2010, 2020 and 2026 era slots, one ID per slot, without reuse. Releases may be banked before an era's year, but its cards remain locked until the minimum calendar year. For this package, only the 1984 entitlement affects live new cards; later slots are reserved by the same rule but add no content. This adopts the candidate policy from [Proposal 019](proposal-019-first-calendar-era-ladder-2026-10-18.md) **only if approved here**.
3. **Card access:** a later-era card is research-admissible only when its named era receipt, own minimum year, all permanently owned parents, ordinary queue/cash requirements and any direct platform rule all hold. A queued parent cannot qualify. The four cards below require no new platform tag; that is a scoped proposal, not a general claim that parents imply compatibility. Existing untagged Features remain on their current access rules.
4. **Visible locks:** show future cards from the outset as locked prospects. Separately name `Year YYYY`, `qualifying player release`, missing parent(s), and current down-payment/finance shortfall where applicable. Do not collapse a future year and missing receipt into one generic lock. A visible card is not an owned card, a project-compatible card, or available project supply.
5. **Receipt identity and saves:** persist versioned receipt assignments keyed to immutable release IDs in the Studio checkpoint and update them in the same committed release transaction. For prior saves, reconstruct only from revision-aware validated frozen release metadata with known Scope meaning and Studio ownership; a missing or ambiguous historical field does not create a receipt. Current checkpoint shape validation alone does not prove frozen `review.scope` and `review.required_scope` are positive, valid integers. Ordinary historical player releases may have no explicit `owner`; infer Studio ownership only for a known revision where that absence has the documented player meaning, never from arbitrary missing data. That Studio may earn a missing receipt with a later qualifying release. Never revoke historical ownership, accepted paid Research, or existing project supply. Unknown receipt versions fail closed while retaining the original save evidence for migration review.

The calendar already starts in 1980 and advances one year per 24 completed productive cycles; the first later-era threshold is 1984 at cycle 96. Calendar waiting without a qualifying release remains insufficient. A qualifying release before cycle 96 remains banked but cannot unlock an era card early. No repeated launch, rejected command or UI browse may mint a second receipt or mutate cash/time/RNG.

## Project, AI and checkpoint behavior

- Completion of paid Research adds ownership only once. It can unlock children and enter supply for **projects begun afterward**; no active hand/project is amended. A Feature remains finite and a draw/play is not guaranteed. The four candidate cards use the normal Design/Alpha Feature pools and are excluded from Primitive-only Contract supply.
- New v4 12-Scope founding rosters and all historical roster versions keep their exact grants. These four are optional Store children. A past owned child remains owned if later catalog metadata changes, but new admissions must satisfy the current approved gates. No silent parent grant or paid-queue reset.
- The player and any AI Store planner must use the same era, parent and quote legality for any node they can acquire. If rival gameplay does not yet support release receipts, a new card stays unavailable to that planner until it can prove the same qualification; it must not bypass the gate or silently change existing AI policy.
- Save and restore the era receipt version, assignments and accepted Research separately from current cash/finance/release facts. Cold Continue, exact replay and rollback must retain receipt identity. If Stage B is not adopted after Stage A, no proposed card ID may leak into the live catalog or saves.
