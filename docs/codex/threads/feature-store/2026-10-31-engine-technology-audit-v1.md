|---|---|---|---|---|

| **B. | **C. ## Recommended responsibility split

1. **Feature Store = studio knowledge.** Preserve all stable Feature IDs, studio-wide paid acquisition, parent graph, era receipts, printed Scope/Core and phase. A Store card represents the studio's ability to make that game Feature, even when its subject sounds technical. Do not create a duplicate Store card to represent an engine tier.
2. **Engine Skill Tree = per-engine support and capacity.** Tier/challenge completion records capabilities of one engine and automatically adds `+5` to that engine's Scope cap once per tier, from its already approved base. It does **not** grant studio ownership of a Feature, pay Store Research, add printed card Core/Scope, or change the project's 30-Scope requirement. Engine node names should describe support/tooling (for example, renderer compatibility or asset pipeline capacity), rather than copy `Text` or `8-Bit Sound` as another purchasable Feature.
3. **Engine Configuration = project supply choice.** At project creation, freeze the intersection of studio-owned, active/future-eligible, engine-supported and engine-enabled Features, retaining the current replacement semantics. Draw only from that frozen eligible set with the existing seven-candidate/four-selection, exhaustion and Pass rules. Configuration changes affect future projects only; a researched but disabled Feature stays owned and retains its familiarity/parents.
4. **No double gate on the foundation.** The proposed Text, 4-Color Palette, Keyboard & Mouse and 8-Bit Sound foundation should be default-compatible with engines that can use them; their existing Store ownership/research must not be charged a second time. A later compatibility gate should describe a genuinely new support limit, with a visible reason and a reachable alternative path.
5. **Keep prerequisite types separate.** Store parents check studio knowledge; engine support checks the selected engine; configuration checks draw eligibility. A child may be configured without forcing its parent into the *same project's draw pool* once the studio has already researched that parent. Do not make Store purchase depend on engine tier, then make that tier challenge depend on purchasing or playing the same child.

## Essential safeguards versus optional redesign

**Essential before any Engine Skill Tree integration:** stable card IDs and legacy records; one source of truth for Store research; explicit support mapping (including default legacy behavior); versioned per-engine tier/cap/challenge and configuration state; immutable project-start supply/engine terms; idempotent `+5` tier milestone; exact 25→30 route that does not require a 30-Scope release to earn the first tier; checks for every current parent chain and era receipt; card-count/weighted-draw/Pass-budget and Review regression comparisons at matched inputs; old/current save and malformed-state rejection.

**Optional after those checks:** card-specific support requirements beyond the four foundation technologies; UI previews of excluded cards and potential Scope/Core/Pass-budget effect; engine-specific challenge variants; gradual support of hybrid cards; a later, separately approved migration of a few true technologies out of the Store. The last option requires replacement prices, Core/Scope compensation, ancestor mapping and frozen-save behavior before any ledger edit.

## Save and progression failure modes to design around

- Current `RunState` owns Feature IDs, paid Research queue, familiarity, era receipts and future supply. `ProjectState` freezes feature supply and review standards. Old ownership, paid installments, active projects, releases and legacy engine selection must remain readable. Do not reinterpret an old owned Feature as a per-engine tier unlock, recalculate a frozen Review or retroactively apply a new capacity cap.
- `16_bit_sound` suppresses `8_bit_sound` only for **future** supply after acquisition. Engine configuration and compatibility need the same temporal boundary; old projects may still contain the 8-Bit card. Retired Audio IDs must stay valid in historical records.
- A licensed 25-Scope engine cannot satisfy the existing 30-Scope qualifying-release receipt. If the first `+5` tier requires that receipt, or a card gated by that receipt, progression deadlocks. First-tier challenges must use already available capabilities/under-cap projects or another independent route; later-tier gates can follow only after the cap is raised and the era path is reachable. The built-in legacy engine remains an uncapped existing-behavior escape route for old/new player Studios under the selected Marketplace rule.
- A configured pool must not silently remove the last positive-Scope Feature or violate phase availability. Show its attainable Scope against the chosen engine cap and the 30-Scope requirement before project start; keep under-Scope warnings/Reviews honest. Preserve Pass Budget generation from **played printed Feature Core**, not from engine tree unlocks or features merely configured.
- Scope cap, ownership, support, enabled set and project supply should be validated in that order. Challenge progress and the `+5` award must have stable per-engine IDs and exactly-once receipts through save/Continue and retries. License terms and royalties belong to the existing Engine Marketplace entitlement/settlement records, not to Store Research or tier completion.
