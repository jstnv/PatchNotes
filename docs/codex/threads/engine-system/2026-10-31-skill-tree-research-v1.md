## Proposed tree and economics

**Each row is four independent branch nodes, not a generation gate on an individual branch.** Its challenge begins after only its own preceding node is purchased. All candidate thresholds count printed primary **plus** secondary Core in that category, from accepted Features using that engine, across Design and Alpha and later games. Costs are paid only after a completed challenge, as an atomic zero-cycle purchase. All four purchases at generation *n* trigger the separate +5 Scope milestone exactly once.

| Generation; capacity after all four purchases | Graphics node / challenge / price | Sound node / challenge / price | Input/Technology node / challenge / price | Text/Design node / challenge / price |
|---|---|---|---|---|
| Foundation; 20 | Text and 4-Color Palette support free | 8-Bit Sound support free | Keyboard & Mouse support free | Text authoring support free |
| **I; 25** | Raster Workflow / **G5** / **$125** | Audio Workflow / **S5** / **$125** | Input Toolchain / **T6** / **$125** | Text Production Kit / **D3** / **$125** |
| **II; 30** | Graphics QA Pipeline / **G10** / **$250** | Sound QA Pipeline / **S10** / **$250** | Technology Regression Harness / **T12** / **$250** | Design Rule Validator / **D6** / **$250** |
| **III; 35** | Raster Asset Pipeline / **G15** / **$450** | Sample Routing Pipeline / **S15** / **$450** | State Adapter / **T18** / **$450** | Branch State Inspector / **D9** / **$450** |
| **IV; 40** | Layer Compositor / **G20** / **$750** | Dynamic Audio Router / **S20** / **$750** | Multi-Device Interface / **T24** / **$750** | Narrative Graph Tooling / **D12** / **$750** |

The challenge numbers and prices are **trial candidates, not approved balance**. Naming is engine tooling/support, not a second paid Text, Palette, 8-Bit Sound or Store Feature card. Foundation support is free on each new proprietary engine, while the same-named Feature cards remain Studio-owned or researched in the Store. There is no generation-wide purchase gate; the milestone merely reads the minimum purchased generation. One accepted Feature with two printed categories can progress both eligible challenges. Neither a Pass nor a synergy can progress a challenge. On purchase, excess progress does not spill into the newly opened child; a retried activation/purchase cannot count twice.

The thresholds deliberately follow the **weakest** of the eight current 12-Scope founder rosters by category: per full-roster release G≥5, S≥5, T≥7, D≥3. This avoids locking Simulation's D3 or RPG's G5 behind a threshold set for Action's G15. It also means specialists may complete their favored branch early; Sound or Design usually limits the whole-generation milestone. A substantial new Feature purchase can speed progression. Prices total **$500 / $1,500 / $3,300 / $6,300 cumulatively** through generations I–IV, before Store acquisition, production, rent or any engine creation cost. The brief specifies no creation cost; this screen assumes $0 and must be rerun if one is proposed.

## Proposed effect arithmetic and stacking

1. **Generation I, one branch:** add 20% of matching **printed Feature Core** to that phase's budget numerator only for Feature activations after purchase. Keep exact integer centi-Core: `effective_centi_core = 100 × ordinary printed Core + 20 × eligible printed category Core`; then `generated = 2 + floor(effective_centi_core / 800)`. The phase's fractional remainder persists through hands/Continue, resets at Design→Alpha, and is never rounded per card. Purchasing a node mid-phase does not retroactively reweight earlier Features. All four branch bonuses add on distinct printed category contributions; a secondary score can qualify. Spent Pass Budget and retained-candidate reservations remain as now. This gives no extra printed Core, Review points, Scope or challenge progress.
2. **Generation II Graphics/Sound:** propose a +10% bonus on the **marginal score produced by matching Pass cards after existing hand production**, with no compounding into Specialization. Calculate the ordinary hand once and its category score with those Pass printed values zeroed but the same selected-card identities/eligibility; the nonnegative difference is the Pass marginal. Accumulate `10 × marginal` in project-local centi-score and grant each new whole bonus point after the ordinary hand score. In a four-identical-Pass hand, ordinary Specialization gives +12; the branch grants +1 extra from 1.2, with 0.2 carried. This avoids `round(2×1.10)=2` making the ability inert, and prevents a second Specialization/Balanced multiplier. The counter resets per project, persists across phases/save and cannot be harvested by redrawing. This exact treatment of mixed Balanced hands is **OPEN** until replay tests prove the marginal attribution; if it misbehaves, narrow the effect to Pass-only hands before approving.
3. **Generation II Technology/Design:** for a played Feature, current pressure is `Scope × total printed Core / 18`. Propose `Scope/18 × [total printed Core − 0.15 × printed Technology Core if Tech II owned − 0.15 × printed Design Core if Design II owned]`. Keep the float through current accumulation/finalization, round Bugs only at the existing final boundary. A T+D card can receive both category reductions on its respective printed portions; a G/T card receives only the T portion. The reduction applies to future activations, not existing pressure/Bugs; Passes do not generate or reduce Feature bug pressure. No global Core multiplier is added.
4. **Generations III–IV:** the proposed distinct gameplay effect is **engine compatibility**, letting researched Store cards enter that engine's configured future-project supply. A concrete *candidate* matrix is below; it adds no card ownership, Core or Scope and does not alter the old built-in/licensed engines or a frozen project. These are **not approved hard Store gates**: apply them to new proprietary engines only after the 20→30 route, weighted draws, era access and save migration are tested. If the gates make previously owned cards feel stranded, reserve these nodes for genuinely new future card families rather than gating current cards.

| Branch | Generation III candidate support | Generation IV candidate support |
|---|---|---|
| Graphics | `8_color_palette`, `animated_sprites` | `split_screen` |
| Sound | `recorded_sounds`, `16_bit_sound` | `dynamic_sequencing` |
| Input / Technology | `save_files`, `multi_directional_scrolling` | `scripted_ai`, `player_level_editor` (still ≥1983) |
| Text / Design | `branching_nodes` | `branching_dialogue`, `multiple_endings` |

The cards remain researched through the Store's existing parents and prices. Their engine support gate never becomes a parent of the challenge that unlocks it: starter Feature printed Core suffices for every branch challenge. This is an optional future support proposal, not a recommendation to remove any current Feature from the Store.

The +5 milestone changes an engine's maximum played Scope, not a Feature's printed Scope or the project's required30. It is granted when the fourth node of a generation is **purchased**, not merely challenge-complete, so the economy cannot be skipped. An engine branch may reach IV while another remains I; capacity then remains25. Existing Store research and owned Feature cards do not automatically become engine nodes or confer Scope expansion.

## Source-derived progression and economic screen

The attached script reads both live card ledgers and extracts the explicit `StudioSpecialties` v5 founder lists/offsets from source. It validates all eight at12 Scope. In an **ideal full-roster exposure** scenario with purchases between games, every founder has enough printed category Core to reach capacities **25 after release1, 30 after release3, 35 after release6, 40 after release10**. This is an arithmetic possibility, **not** a legal ordinary-draw or funded career result. Cards are finite within each project but renew for the next; the model plays each owned starter card once per release. Same-project purchases can accelerate a strong branch, but Sound/Design often constrain the whole tier. Weighted seven-candidate draws, four-card hands, era, cash, Beta/reviews and real sales are not simulated by this script.

The 20-Scope engine **can advance without a 30-Scope release**: every Gen I threshold is reachable from the currently owned 12-Scope starter supply, and under-Scope games are currently releasable with the existing Review penalty. The tier itself does not supply additional Feature Scope. An Action example of five parent-legal Primitive purchases—Scrolling2, Menu System2, Maps2, Dialogue1, Lives System1—adds **8 Scope for $1,950 base** to fill20. A constructive parent-legal +18-Scope route to fill30 adds Character Backstories, Exploration, Secrets, Score System, Enemies, General Combat and Inventory System to those five; total twelve new cards, **$5,750 base research price**. Inventory requires its existing one paid Research action; familiarity/traits can change cash. This route demonstrates reachability, not minimum cost or normal-draw success. It uses Studio Research and does **not** grant cards when an engine tier is purchased.

With neutral variance, zero Bugs and the maximum possible10.0 production rating, the current Review formula caps a20-Scope game at **6.7 displayed Review** (`10×20/30`), a25-Scope game at **8.3**, and a30-Scope game at10.0. Actual Core mix, draws and Bugs lower these ceilings. The first proprietary generation therefore matters for Review capacity, while the starting12 owned Scope limits real early games even further.

An exact 0/1 Scope knapsack over all **24 active Primitive Features** gives single-project category upper bounds at cap20 of **G21/S8/T31/D29**; the same bounds hold at25/30/35 because the category-bearing Primitive subsets fit within20 Scope. This ignores ownership, acquisition parents, draws and hand count, so it is only a ceiling. In particular, Sound IV's cumulative S20 must span at least three Primitive-only games even under ideal ownership, while the engine can still advance by repeating newly available Features in later projects. Later Store Audio can raise that per-game ceiling.

## Feature Store migration decision

**Recommend no card migration in the first implementation.** Engine foundation describes per-engine *support*; the Store cards remain studio-wide *knowledge* and continue to print Scope/Core when played. A free engine node neither buys nor awards the corresponding Store card. The prior [54-card audit](../feature-store/2026-10-31-engine-feature-classification-v1.md) supplies the complete classification. The table below shows why moving even the four obvious foundation cards needs a separately approved catalog and save redesign.

|---|---|---|
| `text` · Scope1 G3 · $300 | Parent of `scrolling` and `colored_text`, transitively `multi_directional_scrolling`/`split_screen`. **Remain**; free Text engine support is separate. | Lose1 Scope/G3/printed3 from Design; parent remap and frozen-save handling required. |

Removing the four foundation cards together would shrink the **active Primitive printed inventory from35 to30 Scope**, erase **G5/S5/T3 =13 printed Core** from Design, and remove their **$1,350** combined base research prices (though all four are already in every current new founder roster). The fresh Action starter would fall from12 to **7** owned Scope and from G15/S5/T7/D5 to **G10/S0/T4/D5**. Its Design printed Core would fall28→15, and generated 2/K8 Design budget5→3 if all remaining cards were played. The optimized Primitive Action Design print50→37, budget8→6; the previously demonstrated eight-Design/four-Alpha 12-Pass construction would lose two Design activations before any replacement balancing. This is a direct numerical reason to preserve Store cards; a 30-Scope *project requirement* remains unchanged. Historical retired Music/Sound Effects IDs and old paid queues/frozen projects must remain decodable even if a later approved migration changes future availability.

## Per-engine state, AI competitors and abuse guards

- Give each proprietary engine a stable, owner-scoped **instance ID**, separate from fixed Marketplace catalog IDs. Store engine owner, version, four branch node purchases, one current challenge counter/completed flag per branch, milestone receipts, configuration and creation/finance receipt. Validate parent purchase, monotone progress, threshold, cap and cash atomically. Derive current capacity from purchased generation minimum; persist receipt for exactly-once grants. Node identity/version and bounded integer counters prevent forged/overflowed saves.
- At an accepted Feature activation, use the project's bound engine ID and printed primary/secondary values to advance only the currently active node in each corresponding branch. Deduplicate by committed action/project ID. A Feature played at a threshold does not also credit its just-opened successor; that successor begins at zero **after purchase**. Retrying a command, restoring a save, redrawing, playing a Pass or applying Specialization creates no extra progress. Completion persists without auto-purchase. Scope milestone grants only after four purchase receipts.
- Engine configuration should select from studio-owned, active, era-eligible, engine-supported Features and freeze supply at project start; purchasing a node or changing configuration does not inject cards into an ongoing project. The engine's cap can rise immediately on a purchase milestone for an already bound active project, but cannot change earlier played Scope, Review standards, cards or score. Apply newly purchased effects only to future accepted activations; preserve previous fractional budget/pass counters. Never reselect a different engine during a project. This active-project behavior is a **proposed integration choice** for approval, not a current rule.
- AI-owned engines need the same instance and purchase/progress records as player engines, with an explicit cash-aware node purchase policy and unchanged Store parent/era rules. Do not grant tiers from a rival's calendar tick or from royalties; only actual accepted Feature activations using its own engine count. For v1, propose that a **creator Studio's own use** advances its engine; licensee usage affects its own games but does not remotely level the creator's engine. A shared-license advancement policy would need separate fairness, ownership and save design. The current two fixed rival Marketplace listings and their creator receipts are not silently converted to proprietary instances.
- Old worlds/projects with `legacy_engine` and licensed engines retain their current entitlement, capacity, royalties, release IDs and frozen project supply. Add a versioned optional proprietary-engine map to Studio/checkpoint schema; missing map migrates to empty rather than fabricating engines/tiers. Preserve old Feature ownership, Research queues, familiarity, era receipts and `16_bit_sound` replacement history. Validate per-engine IDs and no duplicate paid/milestone receipts on Continue. Cross-owner license/royalty settlement remains a separate ledger; no proprietary royalty is charged.

**Deadlocks/exploits to test:** (1) a challenge that needs a 30-Scope qualifying release before the 20→25 or25→30 milestone; this proposal avoids it by counting ordinary starter Features; (2) a support gate on the exact card needed to earn itself; use the starter-compatible foundation and pre-gate candidates; (3) dual-core cards counting twice in a *single* branch, or synergy/Pass accidentally advancing challenges; (4) mid-project purchase/undo/draw replay minting budget, challenge credit or Scope receipts; (5) engine deletion/recreation evading paid progress or bloating saves; (6) a configured pool whose maximum playable Scope cannot satisfy the cap or the 30 requirement; show attainable Scope; (7) new engine buffs making the 2/K8 allowance or Review spike through repeated renewable Pass hands; (8) a free legacy engine making paid proprietary progression unattractive, or AI engines advancing through simulated releases without corresponding expense and card play.

## Phased implementation proposal and acceptance gates

1. **Schema and pure rules:** catalog/instance IDs, foundation support and owner, node definitions, challenge transitions, derived capacity, receipt validation and old-save defaults. No Store card migration. Unit and save/Continue checks for every branch, secondary scores, purchase reset and exactly-once milestones.
2. **Project binding and configuration:** future-project supply intersection and frozen configuration, bound engine identity, capacity20→40, under-Scope warnings and save compatibility. Validate the existing 30 requirement, Store graph/era/replacement, seven-candidate/four-selection/exhaustion and project ownership. Do not launch a config that silently yields no legal path; show eligible printed Scope.
3. **Generation I trial:** current 2/K8 baseline plus centi-Core weighting, phase reset and retained-candidate rules. Matched current-source old/current save and ordinary draw careers across all genres. Confirm actual Pass activations and Review distribution rather than inferring benefit from generated budget.
4. **Generation II trial:** implement Pass marginal attribution and category bug-pressure adjustment only after exact hand/rounding approval. Compare zero/one/both branch effects, mixed and specialized four-card hands, Beta cleanup, Reviews and AI behavior. Keep existing card values.
5. **Balance/adoption review:** isolated simulator versions and seeds for fresh12-Scope player, legal paid Store acquisition to20/25/30/35, current$500 and selected$300 rent, cash/Bank/Contracts, public/legacy/licensed/proprietary engine choices, all eight founder categories, AI rivals and save/replay. Gate node prices/thresholds on actual unlock distributions and affordability; do not approve future III/IV support IDs or any Store migration from this arithmetic screen.

No full current-source Skill Tree headless career exists yet; the artifact here is a deterministic, source-derived **bounds and cost scenario**, with prior career outcomes cited as external baseline. Full gameplay implementation, final balance, migration, UI and release approval remain OPEN.
