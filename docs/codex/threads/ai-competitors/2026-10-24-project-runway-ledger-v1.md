# Rival project runway ledger — 2026-10-24

**Status: SELECTED design direction from the user's 2026-10-24 request; calculation and policy details OPEN. NOT IMPLEMENTED.** The user wants rivals to account for the cost and time of their frozen Feature supply, show spent/total and played/total progress through Design and Alpha, and compare the work left with cash and monthly bills. This record specifies a source-compatible first model. It does not approve a spending threshold, a cycle limit, a UI, or a change to Review/Core scoring.

## Source reconciliation

- A project freezes its owned Feature IDs when it begins (`ProjectState.get_feature_supply_ids()`). `DevelopmentCatalog.get_project_features_for_phase()` separates them by each card's authored Design or Alpha phase. The same Feature ID is not budgeted twice. Later Store Features may lack an approved play price; the live runtime currently charges no play fee for that class. The ledger must mark such prices **UNKNOWN**, not assume that their final price is zero.
- A productive hand selects exactly four *current candidate instances* from a seven-card pool. Features are finite within their phase; Passes can fill slots. A played hand costs the resolver's current exact-cent quote, which can include Lean Production's per-project discount cap. Actual spend comes from the committed transaction/event, not printed values or a hypothetical quote. The existing Store spending guidance estimates an entire prospective pool and observed historical pace for a *player's next project*; it is read-only advice, not an in-project rival budget or a second legality resolver.
- Every successful productive action advances the rival's own calendar one cycle. Two completed cycles form a month; rent is currently $500, or $515 with Expensive Lease. Actual rent, payroll, Bank and education dues are typed ledger obligations. Feature spend is applied before that cycle's sales settlement and due bills. Future sales are uncertain and cannot fund the current hand's preflight. Studio project setup is one productive cycle outside the project's development-cycle count. Phase exits and launch are free when legal. Beta and optional playtests/Research may add productive cycles or direct cash costs.
- The [LOCKED visible-Feature rule](2026-10-24-feature-exhaustion-exit-decision-v1.md) still requires every currently visible legal and affordable Design/Alpha Feature to be played before exit. Planning knowledge of the frozen roster does not let the rival inspect future draws or require Pass-only hands to find hidden cards. A project can therefore leave its phase with a nonzero *unplayed roster* when no current Feature is playable. The previous [forced-Feature study](2026-10-24-forced-feature-finding-v1.md) used current-hand affordability only; it did not prove full-project solvency.

## Proposed ledger and update points

Create one **internal, derived runway ledger** at the Studio project-start decision. After a legal project begins, bind it to project ID and source revision. Keep separate Design, Alpha, and whole-project views; record a reason and `known_price=false` when a quote is unavailable. The initial roster and original estimate are provenance. Recompute the forecast after every committed Feature hand, phase entry, bill settlement, and cash-affecting action. A rejected action changes none of these counters. A restored Studio checkpoint must reconstruct or validate the same ledger without consuming RNG or changing the saved market snapshot.

| Field | Meaning |
| --- | --- |
| `supply_count[phase]` | Frozen phase-eligible Feature IDs for this project. |
| `played_count[phase]` | Distinct Feature IDs actually committed in this phase; never count Passes, redraws, or merely visible cards. |
| `spent_cents[phase]` | Actual committed Feature-play cash charges attributable to that phase, in exact cents. Other costs have their own lines. |
| `remaining_quote_cents[phase]` | Current conditional estimate for each unplayed, known-price Feature once, using the game's pricing path and current trait state. It is not a guaranteed future hand total. |
| `forecast_total_cents[phase]` | `spent_cents + remaining_quote_cents` when all remaining prices are known. Reprice this after transactions; retain the original start estimate separately. |
| `visible_playable_count` | Current hand's Feature maximum under actual four-card legality and present cash; only this can drive the locked exit rule. |
| `remaining_work_hands_min` | `ceil(unplayed Design / 4) + ceil(unplayed Alpha / 4)`, adjusted to zero for phases already legally closed. This is a roster-only lower bound, not a promise that those cards will be dealt together. |
| `known_due_cents` | Already overdue typed bills plus scheduled rent/payroll/Bank/education dues through the forecast horizon, counted once at each real due boundary. |
| `cash_margin_cents` | Spendable cash minus remaining quoted Feature work, known dues, and separately itemized optional/QA allowances. Show **INCOMPLETE** if a price or required horizon is unknown. |

The requested meters can read, for example, **Design Features 6/8; Feature spend $2,600 / $3,400 current estimate** and the same for Alpha, plus a project sum. A denominator that changes because of discounts or newly known prices must say **current estimate**; keep the start estimate and actual spent visible for audit. `spent/total` is descriptive progress, never itself the affordability test. A visible-card count, a frozen-roster count, and the count actually played must remain distinct. Player-facing presentation, if any, is a separate UI decision; the first use is rival policy telemetry and simulator reporting.

## Time and cash calculation

Let `C` be the current completed run cycle and `H` the remaining productive-action forecast. Count month ends as `floor((C + H)/2) - floor(C/2)`; sum the *actual studio's* known dues on those boundaries. At Studio, include one project-start cycle. For a live project, do not count setup again. Add a separately labelled Beta/QA allowance and any explicitly selected optional action; there is no approved fixed amount or number of Beta actions. Keep two time values: a **hard lower bound** from phase-separated Feature counts and a **planning horizon** based on a tested draw/QA policy. If the latter cannot be defended, report it as unknown rather than converting the lower bound into a cash guarantee. No maximum project-cycle count is proposed.

Example only: 15 Features cost a hypothetical **$7,000** in total. If Design has eight and Alpha seven, their four-card lower bounds are two plus two = **four Feature hands**. If the split is five and ten, the bound is two plus three = **five**. Starting at completed cycle 0, one setup cycle + four Feature hands + an *illustrative* two Beta hands uses at least seven productive cycles and crosses three $500 rent boundaries. $9,000 cash minus $7,000 Features minus $1,500 rent leaves **$500** before other bills, optional work, unpriced Features or delayed draws. Starting at completed cycle 1 crosses four rent boundaries in the same seven actions and leaves **$0**. Those are conditional arithmetic examples, not a funded full-project guarantee. A slower draw, a fifth Feature hand, paid QA, or an existing bill can break the plan.

At each actual decision, test the legal hand's exact current cash preflight. The runway forecast also answers whether the project can be *prudently admitted* at Studio and whether optional spending still fits. If the forecast turns negative midproject, reprice and record why; save cash by omitting optional paid actions or future Store admission, and continue the locked visible-Feature behavior while it is legally affordable. If a Feature hand genuinely becomes unaffordable, use the existing legal blocked-state/exit path and retain the unplayed count. Letting a negative forecast **voluntarily skip an otherwise legal and affordable visible Feature** would change the locked rule and remains **OPEN** for an explicit later decision. Do not create an escrow, grant cash, consume future sales, or alter player legality.
