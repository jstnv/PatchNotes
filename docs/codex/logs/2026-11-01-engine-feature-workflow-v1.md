## Cause and repair

`EngineFeatureActions.complete` recorded a paid Feature in the selected engine's `implemented` list but `EngineFeatureState.supply` drew only `committed`. The old global Store required a separate Stage and one-cycle Commit, so an ordinary paid implementation appeared owned yet could not enter a future project draw. The engine-specific quote already used the correct target engine for prerequisites and finance; the UI's Store selector still depended on the project-selected engine.

Completion now atomically records the existing installment/cycle receipt and adds the Feature to that same engine's normalized future supply. The original down payment, FIFO queue, one productive completion cycle, era/prerequisite/cash rules, Studio-wide familiarity and 80% cap remain. No new purchase system or card/balance values were added. The player Stage/Commit commands, AI policy choices, global Studio Store entry, Store engine selector and Commit/respec controls are retired. Internally named research APIs and historical journals remain for compatibility.

Studio Management → Engines shows a Develop New Engine button and Public, licensed, owned and marketplace summaries. Its creation page and engine details are separate. A proprietary detail shows ownership, capacity, implemented library, implementation queue and Skill Tree, and opens its own Feature Implementation Tree without changing the project-selected engine. Public/rival details show fixed libraries and terms read only. The tree labels the existing queue and actions as Implementation and returns to its engine detail. The $100 creation transaction and Skill Tree rules are unchanged.

## Save migration

`engine_features` version 2 derives automatic future supply from paid implementation receipts plus historical configuration state. Version 1 checkpoints still validate. On hydration, only a version 1 record whose effective supply changes is upgraded: active staged or paid but uncommitted Features become available at no extra cost or cycle. An unchanged version 1 record remains byte-semantically unchanged until its next implementation action upgrades it. Previously configured removals remain held unless a later historical event re-added/staged them. This preserves deliberate prior configuration choices and all ownership, staged data, payment/configuration journals and queue order. Version 2 cannot grant a Feature without an implementation or initial-access record. Public/rival fixed manifests, license receipts, royalty records, existing projects and accepted Contracts retain their prior rules.

The one ambiguity left visible is old deliberately removed paid Features: they stay owned but held in the tree. No destructive conversion or new re-enable action was made in this cleanup.

Before optimization the store spent 4.10–4.24 s and semantic validation ran 2–3 times per save, totaling 3.42–3.56 s. The save path reparsed and fully restored unchanged generations during inspect/prune.

`StudioCheckpointStore` now keeps at most three exact positive proofs for generations validated by the detached `CheckpointWriteValidator`. It still checks disk bytes, UTF-8, envelope checksum, sequence and typed DTO equality on every read. A proof is reused only with the same validator source/rules, catalog and publishing source identity; unknown/changed/load validators run full validation. New candidate checkpoints still receive full semantic validation and are written and read back before publication. The worker caches its immutable catalog/context identity within a single write. This removes redundant validation without skipping persistence.
